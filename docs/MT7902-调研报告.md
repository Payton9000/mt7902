# MT7902 板载无线网卡 —— 驱动可行性与作业调研报告

> 调研对象：ASUS B760M-AYW WIFI D4 主板板载 Wi-Fi 6E 卡（MediaTek MT7902）
> 调研主机：test-machine，Ubuntu 22.04.5 LTS，内核 `6.8.0-138-generic`
> 报告日期：2026-09-21
> 本报告性质：**纯调研 + 只读实验**。全程未安装驱动、未修改任何系统配置、未触碰 `/etc`、未重建 initramfs。

---

## 0. 一句话结论

**主板板载的 MT7902 可以在你当前这个 6.8 内核上跑起来 —— 方式是使用「Linux 7.1 主线驱动代码的 backport」，而不是去装 7.1 内核。**

关键实证：我已在本机把该 backport 源码对着你的 `6.8.0-138-generic` 内核头文件编译，**4 秒钟一次通过、零报错**，产出的 `mt7902e.ko` 里设备 ID 恰好是 `14c3:7902`、固件名恰好是 7.1 主线用的那两个、`vermagic` 与运行内核完全一致。

所以对你的问题「7.1 合并的驱动能不能用上／有没有作用」：

> **有作用，而且作用很大 —— 但它的用法不是「升级到 7.1 内核」，而是「7.1 的代码已经被 backport 成一个能在 6.8 上直接编译的独立模块」。**

| 维度 | 结论 |
|---|---|
| 硬件是否损坏 | ❌ 没有。PCI 枚举正常，BAR 已分配，电源状态 D0 |
| 现在为什么用不了 | 内核驱动 ID 表里没有 `7902`，且 MT7902 固件在本机完全不存在 |
| 7.1 内核能不能装 | 能装（mainline 未签名），但**不建议** —— 属大改系统、需重启、可能影响 nvidia DKMS |
| 7.1 的驱动代码能不能用 | ✅ **能，已在本机编译验证通过**，且安全（不动现有任何东西） |
| 主要风险 | ASUS 主板 + AzureWave MT7902 卡有**内核 panic 报告**；以及「硬件锁死」需彻底断电恢复 |
| 蓝牙 | 比 Wi-Fi 难一档（要替换内核 btusb/btmtk），建议作为第二阶段 |

| 项目 | 值 |
|---|---|

### 1.2 蓝牙侧（**走 USB，不走 PCIe**）

这是本次调研最重要的发现之一 —— **MT7902 的蓝牙不在 PCI 总线上，而是通过 M.2 接口的 USB 通道枚举**：

| 项目 | 实测值 |
|---|---|
| USB 路径 | `1-14`（挂在 `0000:00:14.0` xHCI 下） |
| USB ID | `13d3:3596`（IMC Networks，即 AzureWave 的 USB VID） |
| `manufacturer` | **MediaTek Inc.** |
| `product` | `Wireless_Device` |
| 接口数 | 3 个，全部 `class=e0/sub=01/proto=01`（无线控制器） |
| 驱动绑定 | `1-14:1.0` → `btusb`；`1-14:1.1` → `btusb`；`1-14:1.2` → **无驱动** |
| hci 设备 | `hci0` |
| rfkill | `rfkill0`，name=`hci0`，type=bluetooth，soft=0 / hard=0 |

> 注意：你手上的 USB 网卡（`2357:0147 TP-Link AIC8800DC`）**不提供蓝牙** —— `1-6` 只有一个 `class=ff` 接口绑定到 `aic8800_fdrv`。所以目前系统里的蓝牙完全来自板载这张卡。

## 2. 当前为什么用不了 —— 三层根因

### 第 1 层：内核驱动的 ID 表里没有 `7902`

本机实测的 alias 表：

```
mt7921e 支持：0616, 0608, 0b48:7922, 14c3:7922, 14c3:7961     ← 无 7902
mt7925e 支持：0717, 7925                                      ← 无 7902
全盘扫描 /lib/modules/6.8.0-138-generic → 声明支持 14c3:7902 的模块：0 个
```

**因此 `echo 0000:05:00.0 > /sys/bus/pci/drivers/mt7921e/bind` 返回 `ENODEV`（没有那个设备）是完全正确的内核行为** —— 内核在驱动 ID 表里查不到匹配项，直接拒绝绑定。

> 📌 更正记录：此前我把这个 `ENODEV` 归因到 BIOS/rfkill，**方向错了**。真实原因是 ID 表不匹配。

### 第 2 层：固件名被硬编码在模块内部

即使强行往 ID 表里塞 `7902` 也没用 —— 6.8 内核的模块里**根本没有任何 MT7902 固件名字符串**：

| 模块 | 内含的 Wi-Fi 固件名 | 有 7902？ |
|---|---|---|
| `mt7921-common.ko` | `WIFI_RAM_CODE_MT7922_1.bin`、`WIFI_RAM_CODE_MT7961_1.bin` | ❌ |
| `mt7925-common.ko` | `mt7925/WIFI_RAM_CODE_MT7925_1_1.bin`、MT7922、MT7961 | ❌ |
| `btmtk.ko` | `mt7925/BT_RAM_CODE_MT7925_1_1_hdr.bin`、`BT_RAM_CODE_MT7922_1_1_hdr.bin`、`BT_RAM_CODE_MT7961_1_2_hdr.bin`、`mt7668pr2h.bin`、`mt7663pr2h.bin`、`mt7622pr2h.bin` | ❌ |

固件名写在 `.ko` 里（`MODULE_FIRMWARE()` 宏），靠换文件是绕不过去的。

### 第 3 层：MT7902 固件文件在本机完全不存在

```
find /lib/firmware -iname '*7902*'  →  0 个文件
```

原因很直接：Ubuntu 22.04 的固件包是 `linux-firmware 20220329.git681281e4-0ubuntu3.40`（**2022 年的基线**），而 MT7902 固件是 2026 年才进 linux-firmware 的。

## 4. 关于「能不能用上 7.1 的驱动」—— 三条路径的取舍

| 路径 | 具体做法 | 评价 | 理由 |
|---|---|---|---|
| **A. 等发行版升到 7.1** | — | ❌ 不可行 | Ubuntu 22.04 的 HWE 轨道**锁定在 6.8 家族，支持期到 2027-04**；Ubuntu 26.04 LTS 的 GA/HWE 才到 7.0 家族。**Jammy 永远不会拿到 7.1。** |
| **B. 装 mainline 未签名 7.x 内核** | `install.sh --upgrade-kernel` 或手动装 mainline `linux-image-unsigned-*` | ⚠️ 谨慎 | 你的 Secure Boot 已关闭、lockdown=none，**技术上能启动**；但属于"大改系统"：需重启、无发行版支持、可能影响 nvidia DKMS 等出树模块。**不符合你的三条约束。** |
| **C. 用 7.1 代码的 backport（本次已验证）** | 编译 `mt7902e.ko` + 安装 2 个固件文件 | ✅ **推荐** | 不动内核、不动 `/etc`、不重建 initramfs；只新增 **1 个模块 + 2 个固件文件**；可精确回滚。 |

### 为什么说「7.1 的驱动代码」就等于「这个 backport」

`hmtheboy154/mt7902` 仓库自述（一手来源，逐字）：

> "This is basically **the mainline version of mt76** with [patches to support MT7902] & firmware provided by Mediatek. I also stripped down all the unnecessary files & other hardware support to ensure only MT7902 card is supported."

也就是说：**该 backport = 7.1 的主线 mt76 代码（含那 11 篇补丁）+ MediaTek 提供的固件**。

### 本机实测证据：它确实能用在你的 6.8 上

| 验证项 | 结果 |
|---|---|
| 克隆仓库 | ✅ `backport` 分支，HEAD `9d30262` |
| 编译命令 | `make -j20`（`KSRC=/lib/modules/6.8.0-138-generic/build`） |
| 编译结果 | ✅ **4 秒一次通过，0 个 error** |
| 唯一提示 | ① `the compiler differs`（`gcc-12` vs `x86_64-linux-gnu-gcc-12`，**同版本、仅命名前缀不同，无害**）② `Skipping BTF generation ... due to unavailability of vmlinux`（**无害**，内核不要求 BTF） |
| 产物 | `mt7902e.ko`，17,440,952 字节 |

产物的 `modinfo`（决定性证据）：

```
name:      mt7902e
alias:     pci:v000014C3d00007902sv*sd*bc*sc*i*      ← 正好认你的卡
firmware:  mediatek/WIFI_MT7902_patch_mcu_1_1_hdr.bin
firmware:  mediatek/WIFI_RAM_CODE_MT7902_1.bin        ← 正是 7.1 用的那两个
vermagic:  6.8.0-138-generic SMP preempt mod_unload modversions   ← 与运行内核完全一致
depends:   mac80211,cfg80211                          ← 与内核自带 mt7921e 依赖相同
retpoline: Y
```

**它只产出这一个模块**（`src/Makefile`：`obj-m += mt7902e.o`），把所有 mt76 核心代码静态编译进同一个 `.ko`。这一点非常关键 —— 见 §7。

## 5. 三方驱动全景对比

| 方案 | 仓库 / 来源 | 支持内核 | 模块名 | 与 6.8 的适配 | 维护状态 |
|---|---|---|---|---|---|
| **主线（终点）** | Linux 7.1+ in-tree | 7.1+ | `mt7921e` | ❌ 需换内核 | 活跃 |
| **① 首选 backport** | `hmtheboy154/mt7902` | 6.6 ~ 6.19（实测可到 7.0） | `mt7902e` | ✅ **本机已验证可编译** | ⚠️ **已归档**（2026-09-06），作者推荐转 morrownr |
| ② 替代 backport | `morrownr/mt76` | **6.12 ~ 7.x**（`BUILD_EXCLUSIVE_KERNEL` 强校验） | `mt7921e_git` 等（`_git` 后缀） | ❌ **6.8 不在支持范围** | ✅ 活跃维护 |
| ③ 统一安装器 | `abdullaabdullazade/mt7902_driver` | 自动按内核选路 | 视路径而定 | ✅（6.6~7.0 走 ①） | 有 CI 每日同步上游 |
| ④ 厂商 BSP 树 | `hmtheboy154/gen4-mt7902` | 5.4+ | `mt7902` | 可编译但**不稳定** | ❌ **已停止**，作者明确不推荐 |
| ⑤ Wi-Fi+BT 打包 | `OnlineLearningTutorials/mt7902_temp` | 6.14 ~ 7.1 | 自定义 | ❌ 低于 6.14 无对应树 | 中 |

### 5.1 各方案细节

**① `hmtheboy154/mt7902`（本次验证的对象）**

- 安装方式：`make -j$(nproc)` → `sudo make install -j$(nproc)` → `sudo make install_fw`
- `install` 目标：把 `*.ko` 装到 `/lib/modules/$(uname -r)/kernel/drivers/net/wireless/mediatek/mt7902e/`，然后 `depmod -a`
- `install_fw` 目标：把固件放进 `/lib/firmware/mediatek/`（**会跟随系统的压缩格式自动压缩**）
- README 说"装完重启"，**但实际上不需要** —— CNX-Software 的作者在 Ubuntu 24.04 上就是直接 `sudo modprobe mt7902e` 用的
- 蓝牙：另有 `bluetooth_backport` 分支
- ⚠️ 仓库已归档，作者建议内核 6.12+ 的用户改用 morrownr

**② `morrownr/mt76`（不建议用于你的机器）**

- 优点很吸引人：所有模块带 `_git` 后缀（`mt7921e_git.ko`），**与内核模块共存**，配套 `install-driver.sh` / `uninstall-driver.sh` / `check-driver.sh`
- MT7921 家族明确包含 MT7902，PCI ID 表含 `7902`
- ❌ **但 `dkms.conf` 里用 `BUILD_EXCLUSIVE_KERNEL` 强制限定 6.12~7.x** —— 你的 6.8 不在范围内
- 另有 `compat-patches/` 处理 6.12 的 API 变更（`linux/unaligned.h`、`hrtimer_setup()`），说明作者是以 6.12 为起点的
- 结论：**等内核 ≥6.12 时再用它；现在用不了**

**③ `abdullaabdullazade/mt7902_driver`（统一安装器）**

- `install.sh` 的选路逻辑：`modinfo mt7921e | grep 7902` 有命中 → 用内核自带；否则 6.6+ 用 ①；再不行才用内置的 ④
- 它会**自动装 `build-essential linux-headers dkms zstd`**
- ⚠️ 走 fallback（④）路径时，它会 **blacklist `mt7921e` / `mt7902e` / `mt7921_common` / `mt76_connac_lib` 并重建 initramfs** —— 这**违反你的"最小改动"约束**
- 好消息：对我们的 6.8 + ① 路径，**根本不需要 blacklist**（原因见 §7.1）
- 它的 README 有一张很实用的"硬件锁死恢复"表，以及上游 11 篇补丁的 forward-port 对照表

**④ `hmtheboy154/gen4-mt7902`（最后手段）**

- 源自小米 rodin BSP 的 `gen4-mt79xx` 厂商树
- 作者原话（一手，逐字）：

  > "This driver is still in **Work-In-Progress** state! Using it requires extra work... It is **not suitable for everyday use yet**!"
  > "it is not as easy as adding mt7902 info to the driver and expecting it to run smoothly. It turned out that MediaTek gave a **very special firmware** to the MT7921 family"

- 已明确 **discontinued**（"Mediatek has released official patches... I can finally put this project to rest."）
- 已知问题：只能连 2.4GHz、2.4/5 混合 SSID 无法切 5G、WPA3 在 iwd 下失效、无法开热点做中继、编译产物约 100MB、S3 唤醒黑屏、**ASUS 硬件 + AW-XB552NF 卡有内核 panic 报告**
- 结论：**只在 ① 失败后才考虑**

**⑤ `OnlineLearningTutorials/mt7902_temp`**

- Wi-Fi + 蓝牙一起打包，有 `fix_my_wifi.sh` 自动编译
- 一个值得借鉴的设计：它把模块装到 `/lib/modules/mt7902_custom`，**避免动 `/lib/modules/$(uname -r)`** —— 思路很符合你的约束
- ❌ 但它提供的树是 6.14 ~ 7.1，**低于 6.14 没有对应内核树**，覆盖不到你的 6.8

## 7. 风险与隔离性分析（对照你的三条硬约束）

### 7.1 为什么这个方案对现有 USB 网卡是安全的

依赖关系实测：

```
mt7902e        depends: mac80211,cfg80211
aic8800_fdrv   depends: cfg80211,aic_load_fw        ← 只依赖 cfg80211
```

关键点：

1. `mt7902e.ko` **只依赖内核自带的 `mac80211` 和 `cfg80211`，不替换它们**
2. AIC8800 驱动**只依赖 `cfg80211`**，而 `cfg80211` 完全不被本方案触碰 → **USB 网卡零影响**
3. `mt7902e` 是**全新的模块名**（`modinfo mt7902e` 在内核里查不到），**不与任何现有 `.ko` 重名，不覆盖任何文件**
4. 因为它把 mt76 核心（`mt76_connac_mcu.o`、`mt792x_core.o`、`dma.o`、`mac80211.o` …）**静态链接进同一个模块**，所以**不需要**替换内核的 `mt76.ko` / `mt792x-lib.ko` / `mt7921-common.ko`
5. 不需要 blacklist：内核自带的 `mt7921e` 本来就不认 `7902`，两者不存在竞争

> 与那些"要替换整个 mt76 栈"的方案相比，这是**本质区别** —— 也是我推荐它的核心理由。

### 7.2 三条约束逐条核对

| 你的约束 | 本方案表现 | 判定 |
|---|---|---|
| **1. 不影响现有 USB 网卡驱动** | 只新增 `mt7902e.ko`，不改动 `cfg80211`；AIC8800 依赖链完全不受影响 | ✅ 安全 |
| **2. 不删除系统重要文件** | 只**新增** 1 个 `.ko` + 2~3 个固件文件；无需删除/替换任何现有文件；无需 blacklist；无需动 initramfs | ✅ 安全 |
| **3. 全程保持联网** | 编译、加载都独立于 USB 网卡；即便 `mt7902e` 加载失败也只是多一个失败模块，`aic8800_fdrv` 与默认路由不变 | ✅ 安全 |
| （附加）不重启 | 可 `modprobe mt7902e` 现场加载，**无需重启**（已有一手案例） | ✅ 可行 |

### 7.3 ⚠️ 必须知道的风险（均来自一手来源）

## 8. 蓝牙现状与路径（次要目标）

### 8.1 现状实测

```console
$ hciconfig -a
hci0:   Type: Primary  Bus: USB
        BD Address: 00:00:00:00:00:00  ACL MTU: 0:0  SCO MTU: 0:0
        DOWN
        RX bytes:0 acl:0 sco:0 events:0 errors:0
        TX bytes:3 acl:0 sco:0 commands:1 errors:0
        Features: 0x00 0x00 0x00 0x00 0x00 0x00 0x00 0x00
```

判读：**控制器被枚举出来了，但从未完成初始化** —— BD 地址全零、Features 全零、仅发出 1 条命令 / 3 字节、状态 DOWN。这是"固件从未被成功下载"的典型特征。

同时 `/sys/class/bluetooth/hci0/` 下**没有** `name` / `address` / `type` / `bus` 这些属性文件，只有 `device`、`power`、`rfkill0`、`subsystem`、`uevent` —— 进一步佐证 hci 设备处于半初始化状态。

### 8.2 为什么蓝牙更麻烦

| 障碍 | 说明 |
|---|---|
| 6.8 的 `btmtk.ko` 无 MT7902 固件名 | 见 §2 第 2 层表格 |
| 需要**替换**内核的 `btusb.ko` 和 `btmtk.ko` | 不像 Wi-Fi 那样能塞一个独立模块 —— 必须 `rmmod btusb btmtk` 再 `insmod` 自建的 `.ko`，**违反"最小改动"更明显** |
| 社区做法需打内核源码补丁 | 例如向 `btusb.c` 增加 `{ USB_DEVICE(0x0e8d, 0x7902), .driver_info = BTUSB_MEDIATEK \| BTUSB_WIDEBAND_SPEECH }` |
| 你的卡 USB VID 可能不同 | 你的蓝牙是 `13d3:3596`（不是上游补丁里的 `0e8d:7902`），**补丁可能需要按你的实际 ID 调整** —— 这个需要 `dmesg` 才能确认 btusb 到底走了哪条分支 |
| 社区普遍反馈"蓝牙长期几乎为零" | `eriknovikov` 仓库注："at least as of now Bluetooth support for the MT7902 on linux is almost NULL" |

### 8.3 可用的一手资源

- `hmtheboy154/mt7902` 的 **`bluetooth_backport` 分支**（作者自己 tip 的）
- `OnlineLearningTutorials/mt7902_temp`：提供 6.14~6.19 各版本的 patched `btusb.ko` + `btmtk.ko`，做法是 `rmmod` 后 `insmod` 自建模块
- 建议：**蓝牙放在 Wi-Fi 验证通过之后再做**

### 8.4 ★ 精确根因（第二轮实证，已用内核源码 + 内核日志双重确证）

**内核日志实证**（每一次启动都完全一致地复现）：

```
usb 1-14: New USB device found, idVendor=13d3, idProduct=3596, bcdDevice= 1.00
usb 1-14: Manufacturer: MediaTek Inc.
usbcore: registered new interface driver btusb
Bluetooth: hci0: Opcode 0x0c03 failed: -110          ← 关键
```

`Opcode 0x0c03` = **HCI_OP_RESET**；`-110` = **ETIMEDOUT**。即：内核向控制器发 HCI 复位命令，**控制器超时无响应**。

**为什么超时 —— 用 Linux v6.8 源码 `drivers/bluetooth/btusb.c` 确证：**

```c
/* btusb_table[] 第 70–71 行 */
/* Generic Bluetooth USB device */
{ USB_DEVICE_INFO(0xe0, 0x01, 0x01) },          ← 无 driver_info！
```

我们设备的接口正是 `class=0xe0 / sub=0x01 / proto=0x01`，因此命中的是**这条通用条目**，`driver_info` 为空 → `BTUSB_MEDIATEK` 位没被置上 → 于是：

```c
/* 第 4404–4406 行 */
if (IS_ENABLED(CONFIG_BT_HCIBTUSB_MTK) &&
    (id->driver_info & BTUSB_MEDIATEK)) {
        hdev->setup = btusb_mtk_setup;      ← 没执行到
```

`hdev->setup` 保持为 NULL → **不下载固件、完全不调用 btmtk** → 走通用 HCI 初始化，发 HCI Reset → 芯片在无固件状态下不响应 → **超时 -110**。

**再看出真正缺的那一行**（`btusb.c` 第 3116 行起）：

```c
switch (dev_id) {
case 0x7663: fwname = FIRMWARE_MT7663; break;
case 0x7668: fwname = FIRMWARE_MT7668; break;
case 0x7922:
case 0x7961:
case 0x7925:
        snprintf(fw_bin_name, sizeof(fw_bin_name),
                 "mediatek/BT_RAM_CODE_MT%04x_1_%x_hdr.bin",
                 dev_id & 0xffff, (fw_version & 0xff) + 1);   ← 固件名靠命名规律拼出来
        err = btmtk_setup_firmware_79xx(hdev, fw_bin_name, btusb_mtk_hci_wmt_sync);
        ...
default:
        bt_dev_err(hdev, "Unsupported hardware variant (%08x)", dev_id);
        return -ENODEV;
}
```

**没有 `case 0x7902`。**

### 8.5 因此蓝牙所需的改动极小且极明确（2 处，都在 `btusb.c`）

```c
/* [1] btusb_table[] 里加一行，放在 MT7922 段落附近 */
{ USB_DEVICE(0x13d3, 0x3596), .driver_info = BTUSB_MEDIATEK |
                                             BTUSB_WIDEBAND_SPEECH |
                                             BTUSB_VALID_LE_STATES },

/* [2] btusb_mtk_setup() 的 switch 里加一个 case，与 7922/7961 共用分支 */
case 0x7902:
```

**为什么只需这两处**（都经源码核对）：

| 项 | 结论 |
|---|---|
| 固件名要不要另外写 | **不用**。`dev_id = 0x7902` 代入现有 snprintf 格式 → `mediatek/BT_RAM_CODE_MT7902_1_1_hdr.bin`，**与 linux-firmware 里的实际文件名逐字符吻合** ✅ |
| `btmtk.c` 要不要改 | **不用**。v6.8 的 `btmtk.c` 仅 424 行，只导出 `btmtk_setup_firmware_79xx(hdev, fwname, fn)`，**固件名由调用方（btusb）决定**；全文搜 `7902` 命中 0 次 |
| 固件要不要准备 | 要。把 `BT_RAM_CODE_MT7902_1_1_hdr.bin`（509320 字节）放进 `/lib/firmware/mediatek/` |

> ⚠️ 与网上流传的"只加一行 USB ID 就行"的补丁不同：**只加 USB ID 会让设备进到 `btusb_mtk_setup`，然后落到 `default:` 分支报 `Unsupported hardware variant (00007902)` 并返回 -ENODEV**。
> 这正好解释了 lilystar 文章里那条报错 —— 他那个内核（6.19）已经加了 USB ID，但还没有 7902 的 switch case。
> **在我们的 6.8 上两处都必须加。**

## 10. 回滚预案

本方案不改 `/etc`、不改 initramfs、不 blacklist 任何模块，因此**回滚 = 删掉新增的东西**，无残留：

```bash
# 1. 卸载模块
sudo modprobe -r mt7902e

# 2. 删除模块文件
sudo rm -f /lib/modules/$(uname -r)/extra/mt7902e.ko
sudo depmod -a

# 3. 删除固件（可选，留着也不影响系统）
sudo rm -f /lib/firmware/mediatek/WIFI_MT7902_patch_mcu_1_1_hdr.bin \
           /lib/firmware/mediatek/WIFI_RAM_CODE_MT7902_1.bin \
           /lib/firmware/mediatek/BT_RAM_CODE_MT7902_1_1_hdr.bin

# 4. 用 §9 Phase 2.1 的清单核对，确认没有多余残留
ls /lib/firmware/mediatek/ | diff /tmp/fw-before.txt -
```

**兜底**：`6.8.0-40-generic` 内核仍在，可从 GRUB 选择它启动。

**⚠️ 唯一无法靠软件回滚的情况**：出现"硬件锁死"。此时只能**彻底断电**（关机 → 拔电源线 → 长按电源键 30~40 秒 → 重新上电）。

## 16. 第三轮：蓝牙方案落地（补丁 + 编译 + 校验全部完成）

### 16.1 ★★ 最大的坑：发行版内核 ≠ 主线同版本号

我最初拿 `torvalds/linux` 的 **v6.8** tag 源码来编译，结果是**编译失败**：

```
btusb.c:4321: error: 'struct hci_dev' has no member named 'dev_type'
btusb.c:4323: error: 'HCI_PRIMARY' undeclared
btusb.c:4507: error: 'HCI_QUIRK_VALID_LE_STATES' undeclared
```

原因：**Ubuntu 在 6.8 的长期维护期里回移了大量上游后续改动** —— 包括"移除 HCI_AMP"
和"`VALID_LE_STATES` → `BROKEN_LE_STATES`"。所以 Ubuntu 的 6.8 头文件里
压根没有 `dev_type` / `HCI_AMP` / `HCI_PRIMARY` / `HCI_QUIRK_VALID_LE_STATES`。

直接问运行中的内核头文件就能验证：

```bash
B=/lib/modules/$(uname -r)/build
grep -c 'HCI_AMP'                    $B/include/net/bluetooth/hci_core.h   # → 0（已被移除）
grep -c 'HCI_QUIRK_BROKEN_LE_STATES' $B/include/net/bluetooth/hci_core.h   # → 1（改名后的版本）
```

**结论：必须用发行版自己的源码。** 正确路径（已实测可用）：

```bash
# 1) 源码包名与镜像包名不同：jammy HWE 6.8 的源包叫 linux-hwe-6.8
# 2) 到镜像 pool 目录列真实文件名，不要猜 URL
BASE=https://mirrors.tuna.tsinghua.edu.cn/ubuntu/pool/main/l/linux-hwe-6.8
wget -q -O - "$BASE/" | grep -oP 'href="[^"]*"' | sed 's/href="//;s/"//' | grep -E '138|\.dsc|\.tar'
#   → linux-hwe-6.8_6.8.0-138.138~22.04.1.dsc        (8.8 KB)
#   → linux-hwe-6.8_6.8.0-138.138~22.04.1.diff.gz    (9.8 MB，发行版补丁本体，必需)
#   → linux-hwe-6.8_6.8.0.orig.tar.gz                 (219 MB)

# 3) 三个文件下到同一目录，一条命令还原精确源码树（dpkg-source 自带 quilt）
dpkg-source -x linux-hwe-6.8_6.8.0-138.138~22.04.1.dsc
```

**如何确认拿到的是"对的那一份"（比看版本号可靠）**：
把源码里的特征串与**运行中的 `.ko`** 对比，逐条吻合即为同一份。

### 16.2 ★★ 第二个坑：btusb 有**两张**设备表，改错表等于没改

`btusb.c` 里有两张独立的 id 表，**职责完全不同**：

| 表 | 行范围 | 内容 | 是否导出 alias |
|---|---|---|---|
| `btusb_table` | 71 – 176 | **只有通用匹配**（含 `USB_INTERFACE_INFO(0xe0,0x01,0x01)`） | ✅ `MODULE_DEVICE_TABLE(usb, btusb_table)` |
| `quirks_table` | 180 – 844 | **全部厂商专用条目**（Intel / Realtek / Broadcom / MediaTek …） | ❌ 不导出 |

而 `btusb_probe()` 里有这么一段（**关键**）：

```c
	if (!id->driver_info) {
		const struct usb_device_id *match;
		match = usb_match_id(intf, quirks_table);   /* ← 二次查找 */
		if (match) id = match;
	}
```

运行时推演（我们的设备：`bDeviceClass=0xef`，接口 `class=0xe0/01/01`）：

```
btusb_table 首次匹配（usb_match_id 首个匹配即返回）
  行 73 { USB_DEVICE_INFO(0xe0,0x01,0x01) }      → 匹配"设备"类 0xe0；我们是 0xef → 不匹配
  行 79 { USB_INTERFACE_INFO(0xe0,0x01,0x01) }   → 接口匹配 ✓
      （usb_match_one_id_intf 的 0xff 保护条件不成立：0xef ≠ 0xff）
  ⇒ 命中行 79，driver_info = 0
        ↓
btusb_probe: if (!id->driver_info) → 二次查找 quirks_table
        ↓
找到 { 13d3, 0x3596, BTUSB_MEDIATEK }  ⇒ 厂商路径生效 ✓
```

**所以新条目必须加在 `quirks_table`，不是 `btusb_table`。**
所有既有的 MediaTek 13d3 条目（`13d3:3614`、`13d3:3615`、`13d3:3605`、`13d3:3628`…）
都在 `quirks_table` 里 —— 与我们的做法完全一致。

### 16.3 一个"看起来像故障"的正常现象

**打完补丁后，新模块的 alias 列表与系统自带的一模一样（都是 37 条），不会出现 `usb:v13D3p3596...`。**

这不是失败 —— 因为 `quirks_table` **本来就不通过 `MODULE_DEVICE_TABLE` 导出**，
所以它不产生任何 alias。设备匹配是在运行时由 `btusb_probe()` 内部完成的。

> 如果你按"alias 里应该多一条 3596"来判断成功与否，就会误判成失败并白折腾。

## 17. 第四轮：可加载性验证 + 部署/回滚工具化

第三轮证明了两个模块能**编译**。这一轮证明它们能**加载**，并把安装/回滚也做成脚本。

### 17.1 ★ 模块可加载性验证（符号解析法）

**编译通过 ≠ 能加载。** `insmod`/`modprobe` 失败最常见的三种原因是：
vermagic 不匹配、符号版本（CRC）不匹配、**未定义符号找不到提供者**。
前两项已分别用 `vermagic` 与「对着同一份头文件编译」覆盖，
第三项之前没验证过 —— 而它恰恰是出树模块翻车的经典原因。

**方法**（`refs/check_module_symbols.py`，只读、不加载任何模块）：

1. `nm --undefined-only <ko>` 取出该模块的全部未定义符号
2. 从 `modinfo -F depends <ko>` ∪ `modules.dep` 出发，求**依赖传递闭包**
   （注意：未安装的模块在 `modules.dep` 里查不到，所以必须与 `modinfo` 取并集）
3. 收集 `kallsyms`（内核内建符号，本机 320216 个）与依赖链上各 `.ko` 的导出符号
   （静态提取 `__ksymtab_*`）
4. 差集即为**解析不到的符号 → 模块必然加载失败**

**结果：**

| 模块 | 未定义符号 | 依赖闭包 | 判定 |
|---|---|---|---|
| `mt7902e.ko` | 279 | `cfg80211(173)` `mac80211(141)` `libarc4(2)` | ✅ 全部可解析 → 可加载 |
| `btusb.ko`（新） | 130 | `bluetooth(87)` `btintel(18)` `btcms`… `btmtk(6)` `btrtl(8)` `ecc(21)` `ecdh_generic(3)` | ✅ 全部可解析 → 可加载 |
| `mt7921e.ko`（系统自带，**对照组**） | 101 | `cfg80211` `mac80211` `mt76(106)` `mt76-connac-lib(88)` `mt7921-common(16)` `mt792x-lib(62)` | ✅ 全部可解析 |
| `btusb.ko`（系统自带，**对照组**） | 130 | 同新模块 | ✅ 全部可解析 |

**对照组的价值**：两个系统自带模块（已知能正常工作）走同一套判定也全部通过，
**证明这个检测方法本身是有效的**，而不是"什么都能过"。

顺带确认：`mt7902e.ko` **没有任何 `wed` / `mtk_*` 相关未定义符号** ——
虽然 `src/mt76.h` `#include <linux/soc/mediatek/mtk_wed.h>`，
但本机 `CONFIG_MTK_WED` 未启用、`modules.dep` 里也没有 `mtk_wed`，
WED 相关代码被编译成了空操作，不构成加载障碍。

### 17.2 部署 / 校验 / 回滚脚本（`deploy_mt7902.sh`）

按既有约定实现：子命令 `preflight` / `install` / `verify` / `uninstall`，
支持 `--dry-run`，破坏性动作**必须显式 `--yes`**。

内置的安全约束（脚本强制，不靠人记）：

| 约束 | 实现方式 |
|---|---|
| 不重启、不动 initramfs | 脚本里根本没有这两个动作 |
| 不改 `/etc`、不 blacklist | 同上（本方案不需要） |
| 只新增、不覆盖 | 模块装到 `extra/`（Wi-Fi）与 `updates/`（蓝牙），原文件留在 `kernel/` |
| 保住 USB 网卡 | 每一步之后都跑 `net_guard`：检查 `wlxXXXXXX` 是否 UP **且**默认路由是否仍走它，异常立即中止 |
| 可回滚 | 装前记录 `/lib/firmware/mediatek/` 清单到 `/var/tmp/mt7902-deploy.state`；`uninstall` 只删自己新增的；蓝牙额外备份原 `btusb.ko` |
| 失败可查 | `verify` 自动采集内核日志（`dmesg` → `journalctl -k` → `kern.log` 三级回退）并判读 `driver own failed` / panic |
