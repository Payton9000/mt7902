# Bluetooth on MT7902 (Ubuntu 22.04, kernel 6.8)

> **Read this whole page before doing anything.** Unlike the Wi-Fi fixes in this repository,
> the Bluetooth fix requires *replacing a module that ships with your kernel*. That is a
> different risk class. We built and statically verified the patch below but **never deployed
> it** — Wi-Fi was the priority and it worked. Get Wi-Fi stable first.

---

## The symptom

Every boot, without exception:

```
usb 1-14: New USB device found, idVendor=13d3, idProduct=3596, bcdDevice= 1.00
usb 1-14: Manufacturer: MediaTek Inc.
usbcore: registered new interface driver btusb
Bluetooth: hci0: Opcode 0x0c03 failed: -110
```

`0x0c03` is `HCI_OP_RESET`; `-110` is `ETIMEDOUT`. The kernel sent the controller a reset
command and the controller never answered.

`hciconfig -a` shows the wreckage:

```
hci0:   Type: Primary  Bus: USB
        BD Address: 00:00:00:00:00:00  ACL MTU: 0:0  SCO MTU: 0:0
        DOWN
        RX bytes:0 acl:0 sco:0 events:0 errors:0
        TX bytes:3 acl:0 sco:0 commands:1 errors:0
        Features: 0x00 0x00 0x00 0x00 0x00 0x00 0x00 0x00
```

An all-zero BD address, all-zero features, one command sent, three bytes written. The
controller is enumerated but was never initialised — no firmware was ever downloaded.

Also note: **the Bluetooth half lives on USB, not PCIe.** It's `13d3:3596` (IMC Networks,
i.e. AzureWave's USB vendor ID), on the same M.2 slot's USB lanes.

---

## The root cause

Two separate things have to be right, and 6.8 has neither.

### 1. The device matches a generic entry, so no MediaTek path is taken

In `drivers/bluetooth/btusb.c`:

```c
/* btusb_table[] */
/* Generic Bluetooth USB device */
{ USB_DEVICE_INFO(0xe0, 0x01, 0x01) },          /* no driver_info */
```

The card's interfaces are `class=0xe0 / sub=0x01 / proto=0x01`, so it matches that generic
entry. `driver_info` is `0`, so this check never fires:

```c
if (IS_ENABLED(CONFIG_BT_HCIBTUSB_MTK) &&
    (id->driver_info & BTUSB_MEDIATEK)) {
        hdev->setup = btusb_mtk_setup;
```

`hdev->setup` stays `NULL`, so `btmtk` is never called, no firmware is downloaded, and the
chip goes through generic HCI initialisation instead — where a controller with no firmware
running simply doesn't answer `HCI_RESET`. Hence `-110`.

### 2. Even with the right vendor entry, there is no `0x7902` case

`btusb_mtk_setup()` picks the firmware filename with a `switch` on the device ID:

```c
switch (dev_id) {
case 0x7663: fwname = FIRMWARE_MT7663; break;
case 0x7668: fwname = FIRMWARE_MT7668; break;
case 0x7922:
case 0x7961:
case 0x7925:
        snprintf(fw_bin_name, sizeof(fw_bin_name),
                 "mediatek/BT_RAM_CODE_MT%04x_1_%x_hdr.bin",
                 dev_id & 0xffff, (fw_version & 0xff) + 1);
        err = btmtk_setup_firmware_79xx(hdev, fw_bin_name, btusb_mtk_hci_wmt_sync);
        break;
default:
        bt_dev_err(hdev, "Unsupported hardware variant (%08x)", dev_id);
        return -ENODEV;
}
```

No `case 0x7902`. So if you *only* add the USB ID (which is what most patches floating around
do), you get past the ID match and then fall straight into `default:`, printing
`Unsupported hardware variant (00007902)` and returning `-ENODEV`. That error text is a
well-known sight in blog posts about this chip — it's a sign someone stopped one patch short.

The good news: the filename generator needs no change. `dev_id = 0x7902` plugged into the
existing `snprintf` produces:

```
mediatek/BT_RAM_CODE_MT7902_1_1_hdr.bin
```

which is character-for-character the filename in `linux-firmware`. `btmtk.c` on 6.8 is only
424 lines and exports a single function, `btmtk_setup_firmware_79xx(hdev, fwname, fn)`; the
filename is chosen entirely by the caller, so **`btmtk.c` needs no change at all**.

## The fix: two hunks in `btusb.c`

Available as [`patches/btusb/btusb-mt7902.patch`](../patches/btusb/btusb-mt7902.patch):

```diff
--- a/drivers/bluetooth/btusb.c
+++ b/drivers/bluetooth/btusb.c
@@ -661,6 +661,11 @@
 						     BTUSB_WIDEBAND_SPEECH |
 						     BTUSB_VALID_LE_STATES },
 
+	/* MediaTek MT7902 Bluetooth devices */
+	{ USB_DEVICE(0x13d3, 0x3596), .driver_info = BTUSB_MEDIATEK |
+						     BTUSB_WIDEBAND_SPEECH |
+						     BTUSB_VALID_LE_STATES },
+
 	/* MediaTek MT7922A Bluetooth devices */
 	{ USB_DEVICE(0x0489, 0xe0d8), .driver_info = BTUSB_MEDIATEK |
 						     BTUSB_WIDEBAND_SPEECH |
@@ -3255,6 +3260,7 @@
 	case 0x7668:
 		fwname = FIRMWARE_MT7668;
 		break;
+	case 0x7902:
 	case 0x7922:
 	case 0x7961:
 	case 0x7925:
```

The patch is generated by [`tools/make-btusb-patch.py`](../tools/make-btusb-patch.py), which
anchors on **semantic context rather than line numbers** and validates that each anchor is
unique and that the content being added isn't already present. Line numbers in a
distribution's `btusb.c` will drift; anchors won't.

## The two traps

### Trap 1: two device tables, and only one of them matters

`btusb.c` has two independent ID tables with completely different jobs:

| Table | Purpose | Exported as module aliases? |
|---|---|---|
| `btusb_table` | generic matches only, including `USB_INTERFACE_INFO(0xe0,0x01,0x01)` | **Yes** — `MODULE_DEVICE_TABLE(usb, btusb_table)` |
| `quirks_table` | all vendor-specific entries (Intel, Realtek, Broadcom, MediaTek, …) | **No** |

And `btusb_probe()` does this:

```c
if (!id->driver_info) {
        const struct usb_device_id *match;
        match = usb_match_id(intf, quirks_table);   /* second lookup */
        if (match) id = match;
}
```

Walking our device through it (device class `0xef`, interface `0xe0/01/01`):

1. `btusb_table` row 73, `USB_DEVICE_INFO(0xe0,0x01,0x01)` — matches the **device** class, and
   ours is `0xef`, so no match.
2. `btusb_table` row 79, `USB_INTERFACE_INFO(0xe0,0x01,0x01)` — **matches** (the `0xff`
   guard in `usb_match_one_id_intf` doesn't apply, since `0xef != 0xff`), and `usb_match_id`
   returns the first match. So `driver_info = 0`.
3. `btusb_probe` sees `!id->driver_info`, does the second lookup in `quirks_table`, finds our
   entry, and the MediaTek path is taken.

**Therefore the new entry must go in `quirks_table`, not `btusb_table`.** Every existing
MediaTek `13d3:*` entry (`13d3:3614`, `13d3:3615`, `13d3:3605`, `13d3:3628`, …) is in
`quirks_table`, for exactly this reason.

### Trap 2: a "missing alias" that means nothing

After patching, the new module's alias list is **identical to the stock one** — 37 entries,
with no `usb:v13D3p3596...` in sight.

That is not a failure. `quirks_table` is not passed to `MODULE_DEVICE_TABLE`, so it contributes
no aliases at all; matching happens at runtime inside `btusb_probe()`. If you judge success by
"there should be a new alias", you will conclude the patch did nothing and go in circles.

## Building it

**Get the distribution's kernel source, not mainline.** This is the trap that cost us a full
day. Building against the mainline `v6.8` tag fails with:

```
btusb.c:4321: error: 'struct hci_dev' has no member named 'dev_type'
btusb.c:4323: error: 'HCI_PRIMARY' undeclared
btusb.c:4507: error: 'HCI_QUIRK_VALID_LE_STATES' undeclared
```

Ubuntu's 6.8 has already absorbed upstream changes from later kernels (removal of HCI_AMP, and
`HCI_QUIRK_VALID_LE_STATES` renamed to `BROKEN_LE_STATES`). Verify directly:

```bash
B=/lib/modules/$(uname -r)/build
grep -c 'HCI_AMP'                    $B/include/net/bluetooth/hci_core.h   # 0
grep -c 'HCI_QUIRK_BROKEN_LE_STATES' $B/include/net/bluetooth/hci_core.h   # 1
```

The correct source package for jammy's 6.8 HWE kernel is called **`linux-hwe-6.8`** — not
`linux-source-6.8.0`, which is why `apt-get source linux-source-$(uname -r)` finds nothing.
List the mirror's pool directory to see the real filenames rather than guessing URLs:

```bash
BASE=https://mirrors.tuna.tsinghua.edu.cn/ubuntu/pool/main/l/linux-hwe-6.8
wget -q -O - "$BASE/" | grep -oP 'href="[^"]*"' | sed 's/href="//;s/"//' | grep -E '138|\.dsc|\.tar'
#   linux-hwe-6.8_6.8.0-138.138~22.04.1.dsc        (~8.8 KB)
#   linux-hwe-6.8_6.8.0-138.138~22.04.1.diff.gz    (~9.8 MB, required)
#   linux-hwe-6.8_6.8.0.orig.tar.gz                (~219 MB)
```

Put all three in one directory and unpack:

```bash
dpkg-source -x linux-hwe-6.8_6.8.0-138.138~22.04.1.dsc
```

`dpkg-source` brings quilt along itself; no extra packages needed.

**Sanity-check that you got the right tree** — compare string counts in the source against the
`btusb.ko` your kernel is actually running:

| String | Distro source | Running `btusb.ko` |
|---|---|---|
| `Unsupported hardware variant` | 1 | 1 |
| `BT_RAM_CODE_MT%04x_1_%x_hdr.bin` | 2 | 2 |
| `mt%04x/BT_RAM_CODE_MT%04x_1_%x_hdr.bin` | 1 | 1 |

A matching version number is much weaker evidence than matching strings.

Then:

```bash
./tools/build-btusb-mt7902.sh --verify      # check the bundled artifacts first
./tools/build-btusb-mt7902.sh               # patch + compile, does not install
./tools/build-btusb-mt7902.sh --fetch-src   # download and unpack the source if you don't have it
```

Our build result on `6.8.0-138-generic`:

| Item | Value |
|---|---|
| compile | 3 s, 0 errors, `make -j20` |
| output | `btusb.ko`, 1,199,832 bytes (not stripped; the stock one is 180,585 bytes because it *is* stripped) |
| `vermagic` | `6.8.0-138-generic SMP preempt mod_unload modversions` ✓ |
| `depends` | `btmtk,bluetooth,btintel,btbcm,btrtl` — identical to stock ✓ |
| `srcversion` | `8F1F45536AD88F75D09187A` (stock is `336B8A418C3CF8CAEF8D88A`) — proves it's a new build |
| prerequisite | `CONFIG_BT_HCIBTUSB_MTK=y` ✓ (the patch is a no-op without it) |
| entry location | inside `quirks_table` (lines 180–844) ✓ |

## Deploying it (if you decide to)

Firmware first — same `mediatek/` top level as the Wi-Fi firmware:

| File | Bytes | sha256 |
|---|---|---|
| `BT_RAM_CODE_MT7902_1_1_hdr.bin` | 509320 | `4f53b5e02fbd933172e18caf952bda410a877eaad00561781528cb4aff58dc38` |

That file is in `linux-firmware` (version string `20250826211444`, size 509320, matching
byte-for-byte), and also in Debian sid's `firmware-mediatek` and Arch's
`linux-firmware-mediatek` (20260810).

Then:

```bash
# 1. Back up the stock module
sudo cp -p /lib/modules/$(uname -r)/kernel/drivers/bluetooth/btusb.ko \
           /root/btusb.ko.stock-$(date +%F)

# 2. Firmware
sudo cp BT_RAM_CODE_MT7902_1_1_hdr.bin /lib/firmware/mediatek/

# 3. Module into updates/ — this does not overwrite the stock file in kernel/
sudo mkdir -p /lib/modules/$(uname -r)/updates
sudo cp btusb.ko /lib/modules/$(uname -r)/updates/btusb.ko
sudo depmod -a

# 4. Reload (make sure nothing you depend on is using Bluetooth first)
sudo modprobe -r btusb && sudo modprobe btusb

# 5. Verify — the BD address should no longer be all zeros
hciconfig -a
bluetoothctl show
```

**Rollback:**

```bash
sudo rm /lib/modules/$(uname -r)/updates/btusb.ko
sudo depmod -a
sudo modprobe -r btusb && sudo modprobe btusb
```

### One more gotcha

`abdullaabdullazade/mt7902_driver` documents a conflict case: if the Bluetooth firmware is
present twice — for example both `/lib/firmware/mediatek/BT_RAM_CODE_MT7902_1_1_hdr.bin` and
a compressed copy under `/lib/firmware/mediatek/mt7902/` — Bluetooth can fail to come up.
Delete the duplicate.

## Why we didn't ship it

* It replaces a system module, so the blast radius includes Bluetooth keyboards, mice, and
  audio. (On the test machine there were none attached — both input devices were USB
  receivers — so `rmmod btusb` wouldn't have cut the operator's own control channel. Check this
  on your machine before doing it.)
* `CONFIG_BT_HCIBTUSB_MTK=y` is a hard prerequisite; if it isn't set, you get a patched module
  that behaves exactly like the stock one.
* Wi-Fi is what makes the machine usable. Fix that first, confirm it survives reboots, and only
  then consider Bluetooth.

If you do deploy it and it works, a note in the issue tracker would be genuinely useful — we
have not verified this end to end, and the writeup above says so honestly rather than claiming
a success we didn't observe.
